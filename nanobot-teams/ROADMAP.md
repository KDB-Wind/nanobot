# Nanobot Teams：MVP 之后的长程目标

> 前置文档：`ARCHITECTURE.md`、`IMPLEMENTATION_PLAN.md`、`RESEARCH_NOTES.md`。
> 它们定义 MVP 的范围与安全约束；本文件定义 MVP 之后的目标与阶段。
> 冲突时：不改核心、只用公开接口、不伪造持久化这三条以三份文档为准；功能范围以本文件为准。

## 1. 目标状态

用户用一份注册表定义 N 个 bot。每个 bot 是一个独立 Nanobot 实例，拥有自己的
home、config、workspace、身份、模型、skills 和会话。任意两个 bot 在授权图内
可以同步委派任务，结果沿调用链返回。新增或删除 bot 只是配置变更，不改 Nanobot
核心。

对用户的体验应接近 Grok bots：

- **定义**：一份 bot 描述，包含 id、显示名、角色提示、模型 preset、端点、能力、
  允许的调用关系。
- **使用**：向任意 bot 提问；它按需调用其他 bot，用户只看到最终答复和调用轨迹。
- **隔离**：每个 bot 的记忆、会话、工作区互不共享；密钥不跨 bot 传递。
- **可观测**：能看到谁调用了谁、耗时、结果状态；失败有明确分类。

“通信”在本项目中的含义是**由工具调用触发的同步任务委派**，不是自主群聊、
主动推送或无人值守的 bot 对话。后者需要 Nanobot 渠道与核心能力，明确不在本路线内。

## 2. 现状

MVP 已完成并在 Windows 上通过两条入口的验收：

- 单 caller、单 target、单跳、固定线程；
- Registry、端点白名单、Bearer、确定性 session、并发 busy、失败分类、异常阻断；
- skills-only Agent Plugin；独立 stdio MCP；
- 88 个单元/集成测试；服务端 6 个场景 + WebUI 场景可复跑。

尚缺：多 bot 权限图、多跳、预算、任务账本、生命周期工具、发布准备。

## 3. 不可违反的约束

1. 不修改 Nanobot 核心，不 fork，不 import 私有模块，不直接读 session 数据库。
2. 只使用公开 HTTP API、MCP 协议和 Agent Plugin 机制。
3. 不发明上游不存在的能力。没有远端状态、取消、幂等，就只能记录本地观察。
4. 每次委派必须有超时、响应大小上限和日志脱敏。
5. 密钥只从环境变量或配置文件读取，不写入日志，不进入仓库。
6. 每个阶段必须有真实进程的验收；mock 只能补充，不能替代。
7. Windows 和至少一种 Unix 都要记录结果；不能只在一个平台宣称通过。

## 4. 阶段

每个阶段独立可交付、可回滚。上一阶段验收未通过，不进入下一阶段。

### S0：收尾 MVP

- 在一种 Unix 上复跑 `acceptance/run_e2e.py` 全部场景，处理路径与关进程差异。
- 完成 IMPLEMENTATION_PLAN 阶段 6：依赖范围、私有导入/文件写入静态扫描、
  mock 契约回归、支持矩阵、安装/升级/卸载与失败复现说明。
- **完成条件**：两个平台的验收记录、测试通过、README 的支持矩阵更新。

### S1：多 Bot Registry（单跳、多目标）

- `bots[]` 增加 `role`、`capabilities[]`、`allowedCallers[]`、`modelPreset` 等字段。
- caller 不再是全局固定值，而是每个注册项自己的 id；调用方必须出现在目标的
  允许列表中，否则拒绝。
- `list_bots` 返回 id、显示名、角色、能力；不返回端点、密钥或 workspace 路径。
- **验收**：三个 bot（planner/research/writer）任意授权对可委派；未授权对被拒绝；
  并发仍返回 `busy`；端点校验规则不回退。

### S2：多跳与回复路由

- 委派携带信封：`task_id`、`parent_task_id`、`root_task_id`、`hop`、
  `deadline_remaining`。
- 每一跳扣减剩余预算；默认最大 2 跳；用 root + 路径做环路检测。
- 结果沿调用链返回；中间 bot 只看到任务和上游结果，不看到用户身份或密钥。
- **验收**：A→B→C 成功；A→B→A 被拒；预算耗尽返回明确状态；超时不被报为完成。

### S3：Bot 生命周期工具

- `nanobot-teams bot init` 生成 home/config/workspace 骨架和安装清单。
- `nanobot-teams check` 校验 registry、端点、密钥变量、模型 preset、版本兼容性。
- 仍不自动拉起进程；启动由用户执行。若以后要托管，单独决策。
- **验收**：从零生成一个新 bot 并按清单启动；check 能定位端口、密钥、preset 错误。

### S4：任务账本与可观测性

- Teams 自己的 SQLite，只记录本地提交与观察到的结果，不读 Nanobot 私有数据库。
- `list_tasks` / `get_task` 展示本地视图，明确标注“本地观察，不代表远端完成”。
- 结构化日志字段：task_id、caller、target、hop、耗时、结果、字节数。
- **验收**：重启后可查历史；账本不含提示词和密钥；记录与真实结果一致。

### S5：管理与策略

- CLI：`graph`、`budget`、`audit`。
- 每 bot、每链路的调用预算：次数、字节、时间；超预算明确拒绝。
- 可选的只读页面。若仍不能修改核心，就做独立的本地静态页，不冒用官方接口。
- **验收**：超预算被拒；页面只读，不依赖私有接口。

### S6：硬化与发布

- 契约回归（mock + 真实基线）、版本矩阵、wheel、可选 CI、安全审查。
- **验收**：全新环境安装、升级、卸载；不破坏已有会话；文档区分“已实现 / 已测试 /
  不支持”。

## 5. 每个阶段的完成定义

一个阶段只有在以下各项都满足时才算完成：

1. 代码、单元测试、一个真实进程的验收场景；
2. `pytest` 与 `ruff` 通过；
3. README 或 acceptance 文档更新；
4. 记录已知限制与失败复现步骤；
5. `git diff` 确认没有改动 `nanobot-teams/` 之外的文件。

## 6. 执行规则

- 先读三份设计文档和本文件，再动代码。
- 一次只推进一个阶段；阶段内按可验收单元小步提交。
- 遇到上游能力缺口，写 `BLOCKERS.md`：现象、证据、可选方案、影响范围。不要猜。
- 不引入队列、数据库或 Web 框架，除非对应阶段明确要求。
- 不做自主群聊、主动推送、自动拉起 bot、exactly-once 承诺。
- 预算充足不是扩大范围的理由；以验收结果为准。

## 7. 已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 上游没有 run id、状态、取消、幂等 | 多跳只能同步；重启后无法确认远端结果 | 账本只记本地观察；禁止自动重试；文档明确限制 |
| 多跳放大 token 与时间消耗 | 一次用户请求可能触发多级委派 | 每跳预算、最大跳数、deadline 传递 |
| 任意 bot 可被调用 | 越权访问其他 bot 的数据 | 允许图、每 bot 独立密钥、endpoint 仅回环 |
| 注册表膨胀 | 配置错误难定位 | S3 的 check 工具；启动时严格校验 |
| 跨平台差异 | 只在 Windows 验证会掩盖 POSIX 问题 | 每阶段两平台记录；路径与信号单独测试 |
